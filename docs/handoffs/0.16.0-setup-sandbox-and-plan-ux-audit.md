# PMGO 0.16.0 setup, sandbox, and plan-UX audit

Date: 2026-07-28

Consumer observed: AXON

Engine under review: installed PMGO 0.16.0 plus the current
`pmgo-orchestration-engine` checkout

## Executive verdict

Yes—the core orchestration logic appears mostly sound in a normal,
process-capable environment. The DAG loader retains the real dependency edges,
the scheduler can plan independent nodes concurrently, STOP correctly prevents
actuation, and AXON's preserved gate results are legitimate historical
evidence.

The system is not yet a smooth experience for an arbitrary operator or agent.
The most serious gaps are:

1. timeout cleanup becomes unsafe when process enumeration is unavailable;
2. doctor misclassifies permission-denied PID probes as stale processes;
3. the DAG UI presents a parallel dependency graph as a sequential rail;
4. progress combines historical completion with the current delivery campaign;
5. setup, migration, validation, and safe activation remain a multi-command,
   failure-prone workflow;
6. long regression runs are not supervised as resumable, single-instance jobs.

The AXON session also exposed one consumer-specific concurrency configuration
conflict. That is not a general scheduler failure, but it can reduce the
parallelism users actually receive.

## Scope and evidence discipline

This report combines:

- source inspection of the installed 0.16.0 engine;
- source inspection of the current engine checkout;
- the AXON migration and plan-assurance session logs;
- the AXON DAG, gate files, STOP controls, and current PMGO configuration;
- the graph screenshots captured from the PMGO plan workbench.

Findings are classified as:

- **PMGO bug**: incorrect or unsafe behavior in reusable engine code;
- **PMGO UX gap**: technically explainable behavior that is misleading or hard
  to recover from;
- **AXON-specific**: consumer DAG/configuration behavior, not a generic engine
  defect;
- **environmental observation**: not itself an engine regression, but deserving
  a better preflight or diagnostic.

The current engine checkout is dirty with unrelated work. This report does not
claim that an uncommitted implementation is released or verified. Findings
against installed 0.16.0 remain open until covered by regression tests and
shipped in a later version.

## PMGO-001 — DAG renderer falsely serializes a parallel graph

**Severity:** High

**Class:** PMGO bug

**Status:** Fixed in the 0.17.0 line (9a11512), unreleased. Layout is now
dependency-ranked (`rank(node) = 1 + max(rank(dep))`) in a pure
`plugin/assets/plan/dag_layout.js` module that `lens_dag.js` renders, with
equal-rank nodes drawn as one wave and every dependency edge kept.

### Observed behavior

The AXON DAG view renders almost every node on one long horizontal rail. This
strongly implies that one node must finish before the next can begin.

That is not the dependency graph encoded in the DAG.

### Root cause

`plugin/assets/plan/lens_dag.js`, function `computeLayout`, does the following:

1. groups nodes by `stage`;
2. assigns every stage a successive horizontal column;
3. computes longest-path depth using only dependencies whose source and target
   are in the same stage;
4. centers one-node stages on the same vertical row.

AXON uses a distinct stage identifier for nearly every milestone. Therefore
every node receives a separate column and every cross-stage dependency is
ignored for layout depth.

`plugin/scripts/singular_graph_server.py`, function `_stage_sort_key`, compounds
the problem by sorting stages by a D-prefix preference and numeric suffix,
rather than by topological rank. A node can consequently be drawn to the left
of one of its prerequisites.

The server's DAG response still emits correct dependency edges in
`collect_dag_view`; the data model is sound. The defect is the visual placement
and ordering.

### AXON evidence

Ignoring the 13 already-passed historical nodes, the remaining DAG has these
topological waves:

```text
0  G100
1  G110, A100, A110
2  A120, B100
3  B110, B150
4  B120, B130, B160, C100
5  B140, C110, C140
6  B170, C120
7  B180, B190
8  B200, C130
9  B210
10 B220, C150
11 B230
12 C160
13 D100
14 D110
15 D120
16 D130
17 D140
```

The theoretical graph width is four. Practical concurrency is lower because
same-area and overlapping-write-scope work is deliberately serialized, but the
graph is not sequential.

### Required fix

- Compute node rank from all `dependsOn` edges:
  `rank(node) = 1 + max(rank(dep))`.
- Place equal-rank nodes in the same vertical wave.
- Use area swimlanes, or deterministic vertical stacking within each rank.
- Preserve explicit arrows for all dependency edges.
- Topologically order stages or stop using stage order as dependency order.
- Visually distinguish:
  - ready now;
  - blocked by dependency;
  - blocked by human gate;
  - running;
  - historically complete.

### Regression coverage

Add a DAG UI fixture where:

- every node has a unique stage;
- at least two nodes share a dependency and can run in parallel;
- one stage's lexical/numeric order conflicts with dependency order.

Assert that:

- no node is placed before a prerequisite;
- parallel siblings share a rank;
- the maximum rendered width matches the computed frontier width.

## PMGO-002 — Progress conflates historical and current delivery

**Severity:** High

**Class:** PMGO UX gap

**Status:** Fixed in the 0.17.0 line (9a11512), unreleased. Progress is
reported as historical and current-campaign cohorts, with the overall figure
demoted to secondary information.

**Deviation:** cohort membership is DERIVED from the existing `evidenceClass`
field and emitted API-side only. No `campaign` key was added to the on-disk
gate-result schema, so authoritative historical gate files are never rewritten
to make the UI truthful — the report's example payload shape is therefore not
reproduced literally.

### Observed behavior

The workbench reports:

```text
30% — 13 / 44 DAG nodes gated complete
```

while the orchestration loop is stopped and the new plan has not been
actuated.

### Root cause

`plugin/assets/app.js`, near the string `DAG nodes gated complete`, calculates a
single percentage from every passed gate in the active manifest. It does not
distinguish gate provenance or campaign membership.

AXON deliberately retained 13 authoritative historical gate results from
2026-06-21 through 2026-06-26. All have:

```text
status: passed
authoritative: true
evidenceClass: grandfathered
```

Those gates are valid. They were not completed by the current stopped v0.16
campaign.

### User impact

An operator can reasonably infer that:

- the new run already executed work;
- STOP did not prevent execution; or
- green gates were manufactured during setup.

All three inferences are false.

### Required fix

Split progress into explicit cohorts:

```text
Historical accepted: 13 / 13
Current campaign:      0 / 31
Execution:             stopped — pending G100 operator approval
```

The overall `13/44` figure may remain as secondary information, but it must not
be the primary current-run progress indicator.

The graph API should return enough provenance to support this distinction, for
example:

```json
{
  "gate": {
    "status": "passed",
    "recordedAt": "2026-06-25T22:53:13Z",
    "evidenceClass": "grandfathered",
    "authoritative": true,
    "campaign": "historical"
  }
}
```

### Regression coverage

Add a fixture with historical passed gates plus future absent gates and assert:

- historical gates remain green;
- current progress starts at zero;
- stopped state is visible next to progress;
- refreshing the UI does not convert connection liveness into execution
  liveness.

## PMGO-004 — Timeout cleanup is unsafe without `ps`

**Severity:** High

**Class:** PMGO bug / sandbox compatibility

**Status:** Fixed in the 0.17.0 line (1a212a9), unreleased. Cleanup is
session/process-group scoped and no longer needs `ps` to contain a tree;
runners record `sessionSpawn`/`pgid`/`verified` at spawn, and doctor gained
process-control preflight checks that block unattended actuation when safe
cleanup cannot be proven.

**Deviation:** in a group mode with a verified group death, a DENIED `ps`
enumeration does not degrade the result — the kill still reports `verified`,
because the group is the containment and the enumeration was only looking for
escapees. The gap is recorded as an informational `kill.enumeration_unavailable`
event instead of a `degraded` verdict. Tree mode keeps the strict rule, where
enumeration genuinely is the containment.

### Observed behavior

In a restricted sandbox where `ps` is denied, the clean installed v0.16 suite
reproduced timeout case `c10`: the direct child was killed, but its descendant
survived.

The same test passed in a process-capable environment.

### Root cause

Installed `engine/lib.sh`, function `singular_kill_tree` (around line 691 in the
installed 0.16.0 payload), constructs the descendant tree entirely from:

```python
subprocess.run(["ps", "-A", "-o", "pid=", "-o", "ppid="], ...)
```

The return code and stderr are ignored. If enumeration fails, the child map is
empty and only the recorded root PID is signalled.

The current checkout contains the same `ps` dependency in
`engine/lib.sh`, anchor `singular_kill_tree`.

### User impact

- provider or shell descendants may outlive a timed-out agent;
- a surviving process may continue writing to a worktree;
- cleanup can appear successful because enumeration failure is silent;
- unattended operation in restricted environments is unsafe.

### Required fix

Prefer a dedicated process group/session:

1. start each runner in a new session/process group;
2. record PID and PGID durably;
3. terminate the group with TERM, allow a bounded grace period, then KILL;
4. verify group disappearance;
5. use descendant enumeration only as an additional fallback;
6. treat enumeration failure as an explicit degraded/unsafe result.

If a platform cannot provide safe group termination or equivalent isolation,
doctor must block unattended actuation.

### Regression coverage

- Simulate `ps` returning permission denied.
- Spawn a root process with a descendant that ignores TERM.
- Verify both disappear after timeout.
- Verify an unrelated process group is never signalled.
- Verify cleanup reports a distinct failure if it cannot prove termination.

## PMGO-005 — Doctor maps PID-probe permission denial to “stale”

**Severity:** High

**Class:** PMGO diagnostic bug

**Status:** Fixed in the 0.17.0 line (1a212a9), unreleased. The pidfile probe
now returns four verdicts — `alive`, `stale`, `unknown-permission`,
`malformed` — and `EPERM` maps to `unknown-permission`, never to `stale`.

### Observed behavior

Doctor reported AXON console PID `14763` as stale in the restricted sandbox.
Process-capable inspection showed that PID was the live v0.16 graph server.

### Root cause

`engine/doctor.py`, in the pidfile loop near the anchor
`os.kill(pid, 0)`, catches every `OSError` together with invalid data:

```python
except (OSError, ValueError):
    # stale pidfile
```

`PermissionError`/`EPERM` means the process may exist but cannot be inspected.
It is not proof that the PID is stale.

### Required fix

Classify PID probes as a three-state result:

- `alive`: probe succeeds;
- `missing`: `ProcessLookupError` / `ESRCH`;
- `unknown-permission`: `PermissionError` / `EPERM`.

Only `missing` is stale. `unknown-permission` should warn:

```text
PID 14763 exists or is inaccessible; liveness unknown because the environment
denied process inspection. Do not delete the pidfile automatically.
```

### Regression coverage

Mock:

- success;
- `ProcessLookupError`;
- `PermissionError`;
- malformed pidfile content.

Assert four distinct diagnoses and ensure repair never removes an
unknown-permission pidfile.

## PMGO-006 — Setup is not one idempotent, safe workflow

**Severity:** High

**Class:** PMGO UX gap

**Status:** Fixed in the 0.17.0 line, unreleased (implemented, pending its
phase audit and commit). All fourteen prescribed steps are performed, the state
ladder is persisted to `.singular-state/setup/state.json`, and the command ends
with exactly one `Next:` line and STOP still in place.

**Deviation:** the verb is `singular setup`, not `singular bootstrap` — the engine
already uses "bootstrap" for the per-worktree resource bootstrap, and a second
meaning would have collided with it in prompts, config, and events.

**Deviation:** no `approve-actuation` verb was invented. When an approval is
outstanding, setup's one next action routes to the existing human-gate surface
(`singular human-gate status <id>`); otherwise it is `singular resume`, which is
the actuation step the report asks to keep separate.

**Deviation:** step 7's "dry-run the migration and identify destructive
transformations" is implemented at chain-plan level, not staged-execution
level: `singular migrate --dry-run` prints the resolved chain and writes
nothing, but no migration is executed against a shadow copy. Destructive
transformation is instead caught *after* the fact by the pre-migration gate
hash snapshot plus the semantic preservation check (step 9), which fails the
whole command when a historical verdict changed.

### Observed behavior

AXON setup required separate reasoning about:

- repository pin versus installed engine;
- v0 versus v2 schema;
- preservation of authoritative historical gates;
- STOP ownership across old and new state roots;
- migration behavior;
- doctor and regression evidence;
- the difference between migration approval and actuation approval.

The stock migration was not sufficient for AXON because authoritative legacy
gates could not be mechanically rewritten. The safe migration had to be staged
and validated separately.

### Required fix

Add one idempotent command:

```text
singular bootstrap
```

It should:

1. find the repository root;
2. resolve all pin sources and explain conflicts;
3. install the required engine version if absent;
4. detect repository and engine schema versions;
5. create STOP before any migration or scaffold write;
6. snapshot/hash authoritative gates;
7. dry-run the migration and identify destructive transformations;
8. migrate safely or stop with one bounded approval request;
9. verify historical gate preservation;
10. validate config, schemas, DAG, runner, and capabilities;
11. run or attach to the regression suite;
12. persist the regression output and final result;
13. finish in `stopped-ready`, never actuated;
14. print one exact next action.

### Target experience

```text
singular bootstrap

✓ Engine 0.16.0 installed
✓ Repository migrated v0 → v2
✓ Historical gates preserved
✓ Configuration and DAG valid
✓ Runtime capabilities verified
✓ Regression evidence recorded
✓ STOP active; no workers dispatched

Next: singular approve-actuation G110
```

### State model

Expose setup states explicitly:

```text
installed
  → migrated
  → validated
  → stopped-ready
  → explicitly actuated
```

No command should imply that `validated` means `running`, or that installation
implicitly authorizes actuation.

## PMGO-007 — Bash prerequisite handling is inconsistent

**Severity:** Medium

**Class:** PMGO UX gap / environmental preflight

**Status:** Fixed in the 0.17.0 line, unreleased. Interpreter selection lives in
one shared shim (`engine/bash-guard.sh`), adopted by the CLI, the installer, the
migration runner, doctor, and `tests/run.sh`; a Bash <4 selection fails before
any test runs, with the detected path/version and the exact recovery command
under the `SINGULAR_BASH_UNSUPPORTED` code.

### Observed behavior

macOS Bash 3.2 produced cryptic regression failures during the session.

Several engine entrypoints correctly check `BASH_VERSINFO` and either re-exec
through `SINGULAR_BASH_BIN`/Homebrew Bash or print a focused Bash >=4 message.
However, `tests/run.sh` has no equivalent top-level guard and invokes each test
with unqualified `bash`.

### Required fix

- Put interpreter selection in one shared bootstrap shim.
- Make the CLI, installer, migration runner, doctor, and regression harness use
  it consistently.
- Fail before running any test when Bash <4 is selected.
- Print the detected path/version and an exact recovery command.

Example:

```text
SINGULAR_BASH_UNSUPPORTED
Found: /bin/bash 3.2.57
Required: Bash >=4
Recovery: brew install bash && SINGULAR_BASH_BIN=/opt/homebrew/bin/bash singular bootstrap
```

The Bash 3.2 failure is environmental. The absence of one consistent,
early diagnosis is the PMGO UX defect.

## PMGO-008 — Pin/schema mismatch cascades into secondary errors

**Severity:** Medium

**Class:** PMGO UX gap

**Status:** Fixed in the 0.17.0 line, unreleased. Doctor records the schema
mismatch as a blocking primary diagnosis (`SINGULAR_SCHEMA_MISMATCH`) and every
downstream check that would have produced a derivative error skips with an
explicit `blockedBy` pointer back to it, so one incompatibility yields one
diagnosis. `singular setup` reaches the same conclusion earlier, before the
repository is loaded or mutated.

### Historical reproduction

AXON was previously pinned to engine 0.3.0 and schema v0 while the operator was
testing with engine 0.16.0/schema v2. The transitional DAG also represented
G100/G110 in legacy form. That state made v0.16 dispatch unsafe until the G100
migration.

Current AXON is migrated to 0.16.0/v2, so this is no longer an active
AXON blocker.

### Required fix

Resolve the mismatch before loading or validating downstream artifacts:

```text
SINGULAR_SCHEMA_MISMATCH
Repository: engine 0.3.0 / schema v0
Selected engine: 0.16.0 / schema v2
No planning or actuation was attempted.
Recovery: singular bootstrap
```

Avoid emitting multiple derivative errors from the incompatible DAG, prompts,
schemas, and promoter once the primary incompatibility is known.

## PMGO-009 — Regression suites are not resumable supervised jobs

**Severity:** Medium

**Class:** PMGO UX gap / session supervision

**Status:** Fixed in the 0.17.0 line, unreleased, as `singular test`. A detached
supervisor holds an exclusive `flock` for its whole life, so liveness is proved
by the kernel rather than inferred from a pid and `ps` is never consulted; runs
persist under `.singular-state/test-runs/<runId>/` with an atomically-written
`singular.test-run.v0` manifest, per-test logs, and `progress.jsonl`; a second
invocation attaches instead of starting a duplicate, and `--new-run` is the
explicit override; a killed supervisor reconciles to `interrupted` with the
counts it reached.

**Deviation:** the attach verb is `--wait` and there is no `--resume`. Nothing
is resumed mid-suite — a run is either attachable or terminal — so re-running
only what failed is a separate, honestly-named `--rerun-failures`. The manifest
persists run id, pid/pgid, timestamps, engine version/commit, interpreter,
per-test logs, counts, failed names and exit code; the prescribed "capability
profile" field is not recorded, since doctor's report (kept by `singular setup`)
is where capability evidence lives.

### Observed behavior

The original clean regression-suite process continued running after the logged
agent task stopped reporting. A later session could not immediately tell
whether it should start another suite, attach to the existing process, or treat
the missing final output as a failure.

Initialization therefore had not completed, but the visible session looked
finished or abandoned.

### Current implementation

`tests/run.sh`:

- has no single-instance lock;
- writes no durable run manifest;
- does not persist per-test output by default;
- exposes no attach/wait/status command;
- cannot distinguish “runner session stopped reporting” from “suite exited”.

### Required fix

Run the suite through a supervised command such as:

```text
singular test
singular test --status
singular test --wait
singular test --resume
```

Persist:

- suite run ID;
- PID/PGID and process identity;
- start/end timestamps;
- engine commit/version;
- interpreter and capability profile;
- per-test logs;
- final counts and exit code;
- interrupted/unknown state.

Before starting another suite, detect a matching live run. Default to attach or
wait; require an explicit `--new-run` for a concurrent suite.

## PMGO-010 — Git-archive execution needs one explicit rejection

**Severity:** Medium

**Class:** PMGO UX gap / environmental preflight

**Status:** Fixed in the 0.17.0 line, unreleased. `engine/git-preflight.sh`
verifies a real work tree, a resolving `HEAD`, and disposable-worktree support
before the suite starts, and fails once with
`SINGULAR_TEST_SOURCE_UNSUPPORTED` instead of letting every dependent test fail

### Observed behavior

Regression tests executed from a Git archive failed because repository history,

### Required fix

Before the suite starts, verify:

- this is a real Git working tree;
- `HEAD` resolves;

```text
SINGULAR_TEST_SOURCE_UNSUPPORTED

history and disposable worktrees.
Recovery: run from a clean Git clone.
```

Do not let every dependent test fail separately.

## AXON-001 — Conflicting concurrency settings reduce actual throughput

**Severity:** Medium

**Class:** AXON-specific configuration

**Status:** The recommended PMGO hardening is fixed in the 0.17.0 line,
unreleased: doctor detects a structured v2 field and a legacy `env` key setting
the same runtime value differently, and names the effective winner. The AXON
action — choosing one canonical concurrency configuration, bound to G110 —
remains open in AXON and is not something an engine release can close.

AXON's current `singular.config.json` contains:

```json
"env": {
  "SINGULAR_MAX_CONCURRENT": "2",
  "SINGULAR_MAX_DISPATCH": "2",
  "SINGULAR_ENABLE_L1_PARALLEL": "0"
},
"resources": {
  "maxConcurrent": 3
}
```

`engine/lib.sh`, in `singular_json_config_to_env`, exports structured
`resources.maxConcurrent` and then exports the legacy `env` map. The later
`SINGULAR_MAX_CONCURRENT=2` wins.

After G110, the plan intends:

```text
SINGULAR_ENABLE_L1_PARALLEL=1
SINGULAR_MAX_L1_CONCURRENT=3
```

That enables up to three concurrent L1 planners, but worker dispatch remains
capped at two unless AXON reconciles the duplicate settings.

### Required AXON action

Choose one canonical v2 concurrency configuration and remove the contradictory
legacy value. Do not change it while STOP is in place merely to make the UI
look faster; bind the change to G110's explicit actuation approval.

### Recommended PMGO hardening

Doctor should fail or warn when a structured v2 field and a legacy env key set
the same runtime value differently. It should print the effective winner.

## AXON-002 — Same-area serialization is intentional but must be visible

**Severity:** Informational

**Class:** AXON-specific plan/engine constraint

**Status:** Surfaced in the 0.17.0 line (9a11512), unreleased. The console now
reports ready-by-dependency, runnable-now, the concurrency cap, and the
per-node serialization reason, so safe serialization no longer reads as a
broken parallel engine. The constraint itself is unchanged — it is policy, not
a bug.

**Deviation:** the explanation is a read-only console-side REPLICA of
`singular_select_l1_frontier`, not the engine emitting its own reasons. It
models node-lease, area-lease, scope-overlap, and cap — declared in the
payload's `policy` list so the UI never implies more coverage than exists — and
deliberately does NOT model the engine's pending-promotion pre-filter
(`singular_node_pending_promotion`), which depends on supersession chains the
console's task projection does not reconstruct. That omission is fail-open: it
can only show a node as runnable that the engine then skips (and says so in its
own log), never exclude one the engine would have planned.

The scheduler supports parallel L1 planning through
`singular_select_l1_frontier` and `singular_l1_fanout`. It deliberately excludes:

- a node with an active L1 lease;
- a second active node in the same area;
- a node whose write scopes overlap another selected/active lease.

This means AXON's theoretical four-node wave:

```text
B120 (mcp), B130 (mcp), B160 (cli), C100 (platform)
```

has practical width three because B120 and B130 share the `mcp` area.

That is a safety policy, not a scheduler bug. The UI should nevertheless show:

```text
Ready by dependency: 4
Runnable now:         3
Serialized by area:   B130 (mcp area already selected)
Concurrency cap:      3
```

Without that explanation, safe serialization looks like a broken parallel
engine.

## Environmental observations that are not engine regressions

The following results should not be represented as product failures:

- Bash 3.2 syntax/runtime failures when a Bash >=4 path was not selected;
- full-suite failures from a Git archive rather than a clone;
- disk-pressure capacity reducing the effective worker count;
- `ps` denial as an environmental restriction.

However:

- unsafe cleanup after `ps` denial is an engine bug;
- misclassifying `EPERM` as stale is an engine bug;
- allowing Bash/archive problems to cascade into cryptic failures is an engine
  UX gap;
- silently reporting zero capacity without a clear resource diagnosis would be
  an engine UX gap.

## Machine-readable recovery contract

Every preflight/setup failure should include a stable code and one bounded next
action. Suggested shape:

```json
{
  "schema": "singular.operator-failure.v0",
  "code": "SINGULAR_PROCESS_ENUMERATION_DENIED",
  "phase": "runtime-capability-check",
  "state": "blocked",
  "safeToActuate": false,
  "summary": "Process enumeration is unavailable; timeout cleanup cannot be proven safe.",
  "cause": {
    "capability": "process-enumeration",
    "result": "permission-denied"
  },
  "recovery": {
    "command": "singular doctor --json",
    "instruction": "Run in a process-capable environment or configure a verified process-group backend."
  }
}
```

Human-readable output and JSON must identify the same primary failure.

## Prioritized implementation plan

### P0 — Safety and correctness

1. Replace `ps`-dependent timeout cleanup with verified process-group/session
   cleanup and a safe fallback.
2. Add doctor coverage for process enumeration and process-group termination.
3. Correct PID `EPERM` handling to `unknown`, never `stale`.
4. Block unattended actuation when safe timeout cleanup cannot be verified.

### P1 — Truthful orchestration UX

1. Make DAG layout dependency-ranked rather than stage-sequential.
2. Split historical completion from current-campaign progress.
3. Separate data-source connectivity from execution liveness.
4. Show theoretical ready nodes, runnable nodes, concurrency cap, and
   serialization reason.

### P1 — Agent-first bootstrap

1. Add idempotent `singular bootstrap`.
2. Make pin/schema mismatch the sole primary diagnosis.
3. Preserve/hash gates and establish STOP before migration.
4. Persist validation/regression evidence.
5. End in `stopped-ready` and print exactly one next action.

### P2 — Operational continuity

1. Supervise regression suites with a run ID, lock, logs, result, and
   attach/wait/resume behavior.
2. Normalize Bash selection across the CLI, installer, migrations, and tests.
3. Reject Git archives before running the full suite.
4. Detect conflicting structured and legacy configuration values.

## Definition of a smooth setup experience

An unfamiliar agent should be able to enter a consumer repository and safely
reach a verified stopped state without interpreting PMGO internals.

The experience is acceptable when all of the following are true:

- one idempotent command performs or explains every setup step;
- rerunning it causes no duplicate migration, gate rewrite, suite process, or
  state corruption;
- prerequisites fail before mutation;
- every failure has a stable code and one recovery instruction;
- historical evidence is visibly separate from new-run progress;
- current stop/running state is unambiguous;
- the DAG visualization exposes real parallelism;
- the scheduler explains why a ready node is or is not runnable;
- regression output survives the agent session that started it;
- actuation always requires a separate explicit operator action.
