## Objective

`engine/run-status.sh` assigns `lastProgressAt` and `updatedAt` the same `now` on every write
with no predicate — one bit of information in two fields — and during the longest phase of a
run (the blocking runner call between the "Running implementer" and "Running the worker
regression gate" transitions) NEITHER advances, so the field is simultaneously not a liveness
signal and not a progress signal. Nothing even reads it (the health digest sorts on
`updatedAt`). Meanwhile the identities that matter are durable but scattered:
`runner-session.json` (runner pid/pgid), the dispatch record (pid/pidStart/pgid), and
`session-<role>.json` (provider sessionId). This is a correlation defect, not an absence —
so v1 references those records; it does not duplicate them.

Required changes:

1. New additive record `singular.orchestration.run-status.v1`
   (`schemas/run-status.v1.schema.json`), written as `run-status.v1.json` NEXT TO the
   unchanged v0 file (dual-write; v0 stays authoritative for existing readers this release):
   - `processAliveAt` — advanced by observation of the supervised tree (run-dir artifact
     mtime probe and/or pid probe), never by metadata writes;
   - `lastProgressAt` + monotonic `progressSeq` — advanced ONLY on material progress:
     a phase transition, a new per-try artifact, an appended progress/event record, or a new
     evidence artifact; a pure metadata rewrite advances neither;
   - `updatedAt` — last write, as today;
   - `records` — repo-relative refs to the run's dispatch record, `runner-session.json`, and
     `session-<role>.json` files when present (correlation, not duplication).
2. `engine/run-status.sh` computes the v1 fields (carrying forward prior v1 state to decide
   whether progress actually advanced); `engine/l1-drive.sh` call sites need no signature
   change — pure-metadata callers simply won't advance progress.
3. Recovery reads v1 when present: `singular_dispatch_tree_alive` treats a fresh
   `processAliveAt` (within the existing `SINGULAR_TREE_ACTIVITY_WINDOW_SEC` semantics) as one
   more liveness input, and the `SINGULAR_STALE_HARD_MINUTES` hard cap defers — a lease past
   the cap with `processAliveAt` fresher than the activity window logs
   `hard-cap deferred (live)` and is skipped ONCE per cycle rather than reclaimed under a
   provably live tree. Absent v1, behavior is exactly today's.
4. Close the audited coverage gaps in the same task: a live-tree fixture proving
   `recover: skipped (process tree still alive)`, and a `SINGULAR_STALE_HARD_MINUTES`
   boundary test (currently zero tests reference it).

## Acceptance Criteria

- RED first: no v1 file is written; the hard cap reclaims a provably live tree; assert both.
- Two consecutive pure-metadata status writes: `updatedAt` advances, `progressSeq` and
  `lastProgressAt` do not. A phase transition advances `progressSeq` exactly once.
- `processAliveAt` advances during a simulated blocking runner call (stub streaming to the
  run dir) without any status write.
- Live-tree fixture: recovery skips; after the stub dies, reclaim proceeds. Hard-cap boundary:
  past-cap + stale `processAliveAt` reclaims; past-cap + fresh `processAliveAt` defers with
  the logged marker.
- v0 output bytes unchanged for the existing pinned-clock fixtures.
