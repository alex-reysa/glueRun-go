## Objective

Second brick of the executable DAG node `plan-revision-loop` (stage `S3-plan-revision`, area `plancritic`, layer `engine_runtime`, kind `runtime`). The integrated bound authority `gluerun_plan_revise_decide` (engine/ctx-plan-revise.sh) already decides revise / park / import; this brick builds the INPUT that a `revise` decision consumes: the structured-findings revision prompt. It directly implements the requiredCompletion phrasing "revise verdict resumes the node planner with structured findings" and the stage-file phrasing "a revision prompt = base planner prompt + the structured critique findings (per-id) + the prior candidate set". Because the stage file specifies resume-refused falls back to "a fresh planner with the SAME revision prompt", both the resume and the fresh-fallback paths consume exactly this one composed prompt, so building it first unblocks the most downstream work.

New file `engine/ctx-plan-revise-prompt.sh` is auto-sourced by the ctx-loader block in lib.sh and defines NEW functions only; NO existing engine path invokes them, so with the file present-but-uncalled the engine is byte-identical to prior behavior (mirroring engine/ctx-plan-critic-context.sh, whose read-only assembler this brick parallels). It never owns engine/lib.sh and adds no driver-file hook. The GLUERUN_PLAN_CRITIQUE-gated planner re-invocation resuming the persisted node session via gluerun_planner_resume_decide, the rc-86 fresh-fallback record, the per-finding accepted-observation / rejected-observation disposition events (plan.revised with revisesRunId), and the generate-tasks.sh / l1-plan-node.sh driver hooks with the test-ctx-plan-revision.sh full-walk are the sanctioned follow-up slices of this node and are OUT OF SCOPE here.

## Acceptance Criteria

- `gluerun_plan_revise_prompt <node> <critique_record> <stage_dir> <out_file> [template_file]` is PURE and READ-ONLY: it reads the base planner TEMPLATE (from `template_file`, else the canonical planner template resolved by the integrated `gluerun_planner_resume_template_path`, i.e. `GLUERUN_PLANNER_TEMPLATE` or `docs/orchestration/prompts/l1-planner.md`), the `gluerun.orchestration.plan-critique.v0` record at `<critique_record>`, and the prior candidate set (`*.candidate.md` in `<stage_dir>`); it writes ONLY `<out_file>`, appends no events, spawns no runner, and mutates nothing else. Empty `<out_file>` returns non-zero (usage).
- The composed prompt contains three clearly-headed sections in a stable, deterministic order: (a) the base planner TEMPLATE body verbatim; (b) a structured findings section listing EVERY entry of the record's `findings[]`, each rendered with its exact `id` (the `f-[0-9a-f]{12}` identifier), `severity`, `claim`, `evidence`, and `suggestedChange` when present, sorted by `id`; and (c) the prior candidate set: every `*.candidate.md` body in `<stage_dir>` in sorted glob order. The verbatim per-id ids are preserved so the later disposition slice can map each finding to `accepted-observation` / `rejected-observation`.
- Determinism: for a fixed input set the output is byte-identical across repeated runs (id-sorted findings, sorted candidate glob, no timestamps or nondeterministic ordering).
- Fail-safe without fabrication (evidence invariance): a missing or unreadable template, a missing / unparseable / schema-divergent critique record, or an empty candidate directory each degrade to that section being present but explicitly marked empty (e.g. a `no parseable findings` / `no prior candidates` marker) rather than crashing; the assembler NEVER fabricates findings or candidates and never silently emits a prompt with the findings section absent, so a downstream planner is never flown blind under the guise of a normal prompt.
- The file defines new functions only and is invoked by no existing engine path: `tests/test-engine-clean.sh` stays green and an unused run is byte-identical to current behavior (no events, no state writes, no runner invocation).
- Strict-test-first: `tests/test-ctx-plan-revise-prompt.sh` is authored red first (asserting the above before implementation) and green after, running against isolated state (real run state untouched); the full suite `bash tests/run.sh` is green. Cases covered: TEMPLATE body included verbatim; every finding rendered with its exact id / severity / claim / evidence (+ suggestedChange when present) in id-sorted order; prior candidates included in sorted order; two runs byte-identical; missing template, unparseable record, and empty candidate dir each degrade to marked-empty sections without crashing; usage error on empty out_file.
- Gate candidate: with this slice integrated, `plan-revision-loop` has the structured-findings revision prompt that both the resume and the fresh-fallback paths consume; the node gate remains BLOCKED pending the resume-vs-fresh planner re-invocation, the rc-86 fresh-fallback record, the per-finding disposition events, and the generate-tasks.sh / l1-plan-node.sh driver-hook slices with test-ctx-plan-revision.sh full-walk coverage.
