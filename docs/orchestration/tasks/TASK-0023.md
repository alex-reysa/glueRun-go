## Objective

Fifth (composition) brick of the executable DAG node `plan-revision-loop` (stage `S3-plan-revision`, area `plancritic`, layer `engine_runtime`, kind `runtime`). All four engine-side helpers are integrated: the bound decider `singular_plan_revise_decide` / `singular_plan_revise_max` (TASK-0019), the structured-findings revision prompt assembler `singular_plan_revise_prompt` (TASK-0020), the per-finding disposition classifier + `plan.revised` events `singular_plan_revise_*dispositions` (TASK-0021), and the revision-round resume/fresh strategy + rc-86 fresh-fallback recorder `singular_plan_revise_resume_decide` / `singular_plan_revise_record_strategy` / `singular_plan_revise_record_resume_failed` (TASK-0022). The plan-critic driver `singular_ctx_plan_critic_run` (TASK-0013) is also integrated. What is still missing is the piece that composes them into the actual bounded in-lineage loop and the canonical full-walk test the requiredCompletion cites.

This brick adds a single composed orchestrator that runs, over a node's STAGED candidate set, the bounded revise -> (resume|fresh) -> re-critique -> approve/park loop by calling ONLY those integrated functions, mirroring the composed-orchestrator precedent engine/ctx-critique-import-fanout.sh (TASK-0017). New file `engine/ctx-plan-revise-loop.sh` is auto-sourced by the ctx-loader block in lib.sh and defines NEW functions only; NO existing engine path invokes them, so present-but-uncalled the engine is byte-identical to current behavior. It adds NO driver-file hook and never owns engine/lib.sh. The planner and critic are reached through their existing runner indirections so the loop is fully stubbable. The single SINGULAR_PLAN_CRITIQUE-gated minimal call-site hook in l1-plan-node.sh that invokes this orchestrator after staging is the sanctioned final follow-up slice of this node and is OUT OF SCOPE here.

## Acceptance Criteria

- `singular_plan_revise_loop <node> <run_id> <stage_dir> [worktree]` composes ONLY integrated functions into the bounded in-lineage revision loop over the staged `*.candidate.md` set: it runs the plan-critic via `singular_ctx_plan_critic_run`, then each round applies `singular_plan_revise_decide` (SINGULAR_PLAN_REVISE_MAX default 1) to map the critic verdict plus rounds-already-spent to import / revise / park. It prints EXACTLY one terminal outcome line, `import` or `park <reason>`, and drives no state beyond the stage dir and the event log.
- approve -> import: a critic `approve` verdict (at round 0 or after a revision) terminates the loop returning `import` with the current staged candidate set left intact for L0; no revision is attempted.
- revise within budget -> one bounded revision round: on `revise` with budget remaining the loop (a) assembles the revision prompt via `singular_plan_revise_prompt` (base planner template + structured per-id findings + prior candidate set); (b) decides resume-vs-fresh via `singular_plan_revise_resume_decide` and records it via `singular_plan_revise_record_strategy`; (c) re-invokes the planner through the injectable planner runner, resuming the persisted node session else fresh with the SAME revision prompt, to re-stage candidates; (d) on a resume runner rc-86 exit falls back to a fresh re-run and records it via `singular_plan_revise_record_resume_failed`; (e) records the revised batch's per-finding dispositions via `singular_plan_revise_record_dispositions` (`plan.revised` + accepted-observation / rejected-observation / accepted-but-unaddressed); then re-critiques the revised candidates.
- budget exhaustion -> park: once the effective `SINGULAR_PLAN_REVISE_MAX` revisions have run and the verdict is still non-approve, `singular_plan_revise_decide` returns park and the loop terminates as `park revise-budget-exhausted` (recorded); an explicit `park` verdict likewise terminates as `park`.
- Feature-flag + evidence invariance: the loop is meaningful only under `SINGULAR_PLAN_CRITIQUE=1`; the file defines new functions only, is invoked by no existing engine path, and present-but-uncalled leaves the engine byte-identical (`tests/test-engine-clean.sh` green). The loop affects PLANNING only: it never promotes candidates to the global tasks dir itself (L0 stays the sole importer), never weakens a resume or import gate, never makes the fresh implementation auditor bypassable, and keeps the critic read-only / fresh-by-default. Events route only to the pinned `SINGULAR_EVENTS_FILE`.
- Strict-test-first: `tests/test-ctx-plan-revision.sh` (the canonical node test named in the requiredCompletion) is authored red first and green after, fully hermetic with STUB planner and STUB critic runners (pins `SINGULAR_EVENTS_FILE`, the stage dir, `SINGULAR_PLAN_CRITIQUE=1`, and `SINGULAR_PLAN_REVISE_MAX`); the full suite `bash tests/run.sh` is green. It exercises the full walk: critique -> revise -> approve -> import; budget exhaustion -> park; the resume path AND the rc-86 fresh-fallback path both covered; and every disposition (accepted-observation, rejected-observation, accepted-but-unaddressed) plus the `plan.revised`, strategy, and resume_failed events observable in the event log.
- Gate candidate: with this slice integrated, the executable DAG node `plan-revision-loop` (layer `engine_runtime`) has an end-to-end bounded revise -> (resume|fresh) -> re-critique -> approve/park loop passing the full-walk `test-ctx-plan-revision.sh` on stubs with every disposition event-visible, matching the requiredCompletion behavior and the stage-file exit gate; the only remaining wiring is the single SINGULAR_PLAN_CRITIQUE-gated minimal call-site hook in l1-plan-node.sh that invokes `singular_plan_revise_loop` after staging. The node gate stays BLOCKED until that hook lands and the walk is gate-recorded; this task does not declare the node complete.
