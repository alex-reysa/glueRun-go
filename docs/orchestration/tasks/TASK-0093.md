## Objective

Advance the `experiment-run` executable DAG node (layer `evaluation`) with the arm-configuration provenance the measurement suite lacks. The whole output side is integrated — the raw-metric aggregators (TASK-0077/0079/0081), the summary merge (TASK-0083), the arm-delta (TASK-0089), the renderer (TASK-0085), the end-to-end guard (TASK-0087), and the `gluerun experiment-report` CLI (TASK-0091) — and all of it attributes escape-rate/cost/bias to arm A vs arm B, yet NOTHING records which continuity features were actually active for a run. requiredCompletion defines the arms by their knob-state (`control = M0 knob-state`, `treatment = critique+revision+packets+routing`), and the experiment's validity hinges on each arm being correctly configured; a durable per-run knob-state snapshot is the auditable evidence for that attribution. This task ships a deterministic, strictly read-only emitter of the OBSERVED continuity knob-state — it does NOT prescribe a profile, run the paired-audited A/B experiment, author `docs/context-build-plan/experiment-report.md`, or record per-knob default decisions in `docs/orchestration/decisions.md`, all of which are OPERATOR authority (kind: evaluation). It neither declares nor gates node completion.

All logic lands in one NEW `engine/ctx-experiment-armstate.sh`, auto-sourced by the ctx-loader block and defining new functions only. No existing engine path invokes them, so the engine is byte-identical with the file present (OFF-parity intrinsic, mirroring the sibling `engine/ctx-experiment-*.sh` idiom). It reads ONLY the process environment (the engine's own `GLUERUN_*` continuity knobs) and creates, moves, or mutates nothing — it appends NO event and writes no file (a per-run recorder wired into `l1-drive.sh` would own a pre-existing driver file and is a separable out-of-scope slice). It does NOT edit the sibling `ctx-experiment-*.sh` files or any pre-existing file.

Implement three chained slices in order, all inside `engine/ctx-experiment-armstate.sh`:

1. Pure knob-reader helper: for a canonical continuity-knob name, read its environment value with the knob's documented default and produce a record {knob, value, active} where `active` is the boolean interpretation (set-and-enabling versus unset / 0 / empty). Deterministic.

2. Snapshot consumer: apply the helper across the engine's continuity feature knobs that distinguish treatment from the M0 control baseline — `GLUERUN_CTX_PACKET`, `GLUERUN_CTX_ROUTING`, `GLUERUN_REHYDRATE`, `GLUERUN_PAIRED_AUDIT_PCT`, `GLUERUN_CRITIC_RECHECK_PCT`, and the optional `GLUERUN_CTX_ARTIFACT_SCAN` and `GLUERUN_CTX_MANIFEST` — using exactly the canonical names the engine defines.

3. Composed emitter `gluerun_ctx_experiment_armstate_json`: assemble the snapshot into ONE deterministic sorted-key JSON object conforming to a NEW additive schema `gluerun.orchestration.ctx-experiment-armstate.v0`. With no continuity knobs set the object IS the M0 control knob-state (every knob inactive); with the treatment knobs set it is the treatment knob-state — one emitter documents either arm by reading the environment.

## Acceptance Criteria

- `tests/test-ctx-experiment-armstate.sh` is red before implementation and green after; the gate command is green.
- With all continuity knobs unset, `gluerun_ctx_experiment_armstate_json` emits the M0 knob-state snapshot: every continuity knob reported inactive at its documented default — the control-arm state.
- With the treatment continuity knobs set (for example `GLUERUN_CTX_PACKET=1`, `GLUERUN_CTX_ROUTING=1`, `GLUERUN_REHYDRATE=1`, `GLUERUN_PAIRED_AUDIT_PCT=25`, `GLUERUN_CRITIC_RECHECK_PCT=25`), the snapshot reports each of those knobs active with its observed value — the treatment-arm state.
- The output is a single JSON object with sorted keys, deterministic for a fixed environment, that validates against `schemas/orchestration/ctx-experiment-armstate.v0.schema.json` (emitted-conformance guard); each entry carries the knob's canonical name, observed value, and boolean `active` interpretation.
- Fail-safe: a partial or non-enabling value (non-numeric percent, empty string) is reported verbatim with `active` false where it does not enable the feature, never a nonzero exit or partial output.
- Strictly read-only: the emitter reads only the environment; the test asserts it creates, moves, or mutates no run artifact, index, event, lease, or task file, appends no event, and writes no `docs/context-build-plan/experiment-report.md`. No test contains a temporal negative / present-but-uncalled assertion (planner-contract rule 9); read-only and OFF-parity guarantees are pinned behaviorally over the environment fixtures, not by absence greps.
- The new schema is additive under the `gluerun.orchestration.*.v0` namespace and validation fails closed. `tests/test-engine-clean.sh` stays green: only the engine's own `GLUERUN_*` knobs are named (no project-specific symbols in `engine/`).
- Gate candidate (does not itself complete the node): this knob-state snapshot is the per-arm configuration provenance `experiment-run`'s report attributes escape-rate, cost, and bias to (control = M0 knob-state versus treatment); node completion still requires the operator to run the paired-audited A/B experiment across both arms and record per-knob default decisions in `docs/orchestration/decisions.md`.

## Context packet

### Decisions

- Emit an OBSERVED knob-state snapshot (provenance) rather than a PRESCRIBED arm profile, so the brick records which continuity features were actually active for a run (auditable evidence) without usurping the operator's judgment about how to configure each arm.
- With no continuity knobs set the snapshot IS the M0 control knob-state (all inactive) and with the treatment knobs set it is the treatment state, so one emitter documents both arms by reading the environment — matching requiredCompletion's control/treatment knob-state language.

### Rejected alternatives

- A prescriptive fixed treatment-profile emitter — rejected: the exact arm configuration (which knobs, which percentages, on which corpus) is operator run-config; hardcoding it in `engine/` risks drift and trespasses on operator judgment.
- Wiring a per-run knob-state recorder into `l1-drive.sh` — rejected here: that owns a pre-existing driver file (full-suite gate) and is a separable slice; this bounded brick ships the pure emitter only.

### Assumptions

- [validated] The engine exposes continuity feature knobs as `GLUERUN_*` environment flags: `GLUERUN_CTX_PACKET`, `GLUERUN_CTX_ROUTING`, `GLUERUN_REHYDRATE`, `GLUERUN_PAIRED_AUDIT_PCT`, `GLUERUN_CRITIC_RECHECK_PCT`, and the optional `GLUERUN_CTX_ARTIFACT_SCAN` and `GLUERUN_CTX_MANIFEST` — basis: grep of engine/*.sh and cli/gluerun.
- [open] The worker must enumerate EXACTLY the continuity knobs the engine actually defines (reading their canonical names from the engine), not invent knob names; if a plan-critique/revision enable flag exists under a different canonical name, include it, else omit rather than fabricate — basis: keep the snapshot faithful to real engine knobs.
