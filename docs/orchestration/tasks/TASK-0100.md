## Objective

Advance the `experiment-run` executable DAG node (layer `evaluation`) with the presentation capstone: one command that emits the COMPLETE experiment-report body markdown. Two corpus renderers are integrated — `singular_ctx_experiment_pipeline_md` (TASK-0087: the per-arm escape/cost/bias, strategy, and attempts tables) and `singular_ctx_experiment_render_result_md` (TASK-0098: the treatment-effect delta and arm-integrity audit tables) — but to author `experiment-report.md` the operator must invoke both separately and hand-order/concatenate their output. This composes them into ONE ordered report-body markdown the operator pipes into the report. It emits markdown to STDOUT ONLY; it never writes `docs/context-build-plan/experiment-report.md` (an operator-owned concept), never runs the paired-audited A/B experiment, and never records per-knob default decisions in `docs/orchestration/decisions.md` — all OPERATOR authority (kind: evaluation). It neither declares nor gates node completion.

All logic lands in one NEW `engine/ctx-experiment-report-body.sh`, auto-sourced by the ctx-loader block and defining new functions only. No existing engine path invokes them, so the engine is byte-identical with the file present (OFF-parity intrinsic, mirroring the sibling `engine/ctx-experiment-*.sh` idiom). It does NOT edit the sibling `ctx-experiment-*.sh` renderers, `cli/singular`, or any other pre-existing file. It composes the two integrated corpus renderers verbatim (no recomputation, no reformatting of their table content) and reads or writes nothing else.

Implement two chained slices in order, both inside `engine/ctx-experiment-report-body.sh`:

1. Section-composition helper: assemble the two rendered fragments under stable section headers in a fixed order — the per-arm metrics section first, then the treatment-effect and arm-integrity section — preserving each fragment's content verbatim.

2. Composed public entry `singular_ctx_experiment_report_body_md [runs_dir] [events_file] [metrics_file]`: obtain both fragments by delegating to `singular_ctx_experiment_pipeline_md` and `singular_ctx_experiment_render_result_md` over the SAME resolved corpus args, compose them via the helper, and emit the complete body to stdout. Deterministic; fail-safe: an empty corpus renders a well-formed body with zeroed tables and a zero exit.

## Context packet

### Decisions

- Compose the two integrated CORPUS renderers `singular_ctx_experiment_pipeline_md` and `singular_ctx_experiment_render_result_md` (both take explicit `[runs_dir] [events_file] [metrics_file]`, so ordering over one resolved arg set is consistent) into a single ordered body, rather than re-rendering — each section keeps one upstream definition site and the body cannot drift from the section renderers.
- Emit markdown to STDOUT and never write `experiment-report.md`, because that file is an operator-owned concept; the composer is presentation tooling the operator pipes into the report, not the report author.
- Ship a SEPARATE new file rather than a `cli/singular` subcommand, keeping this additive, new-files-only, and free of any owned-file overlap with concurrent CLI work.

### Rejected alternatives

- Writing `experiment-report.md` directly — rejected: operator-owned file/concept; the planner contract keeps eval doc authorship operator-driven.
- A `singular experiment-report body` CLI subcommand — rejected here: it would own `cli/singular` (a pre-existing driver file, full-suite gate, and possible overlap with concurrent CLI work); a new engine file avoids both.

### Assumptions

- [validated] `singular_ctx_experiment_pipeline_md [runs_dir] [events_file] [metrics_file]` (per-arm tables) and `singular_ctx_experiment_render_result_md [runs_dir] [events_file] [metrics_file]` (treatment-effect + arm-integrity) are integrated and each emit a deterministic markdown fragment — basis: engine/ctx-experiment-pipeline.sh (TASK-0087) and engine/ctx-experiment-render-delta.sh (TASK-0098) public entries.
- [open] A sparse corpus may leave one section with only zeroed tables; the composer still emits both sections under their headers rather than omitting one — basis: the fail-safe contract of the delegated renderers.
