## Objective

Gate execution duplicates a worse version of the supervised-job machinery, twice:
`engine/gate-check.sh` (spawn via `singular_setsid_exec`, hand-rolled `kill -0`/`sleep 2` poll,
kill-tree at deadline) and `engine/audit-verify.sh` (same shape, different timeout, different
0.1 s poll, different grace). Neither takes a lock, so two identical gates both run; neither
writes an in-flight record, so a killed launcher leaves nothing to reconcile; and
`gate-check.sh` deletes the previous observation/report/summary before it knows anything —
actively hostile to any reuse. Meanwhile rel-11 provides the primitive and rel-12 the identity.

Required changes:

1. Route both gate execution paths through `engine/supervised_job.py`: the supervised command
   is the gate command exactly as today (same env injection, same `SINGULAR_GATE_REPORT_FILE`
   observation contract, same timeout semantics via the primitive's deadline + the rel-07
   run-control re-read).
2. Compute the pre-execution job identity via `engine/identity.py::job_identity` (task, run,
   role, canonical argv, env allowlist, workspace, headSha, declared input hashes). A second
   launch with IDENTICAL identity attaches and shares the result; ANY identity drift starts a
   fresh job. Result reuse across completed jobs is NOT enabled in this task — attach applies
   to in-flight jobs only; a completed job's result is reused only within the same drive
   invocation that launched it.
3. Move the `rm -f` of prior observation/report/summary to AFTER the attach/fresh decision,
   and only on the fresh path.
4. Collapse the duplicated spawn/poll/kill blocks: `audit-verify.sh`'s loop delegates to the
   same primitive with its own timeout/grace parameters preserved as configuration, not as a
   second implementation.
5. Interrupted reconciliation: a gate whose supervisor dies reconciles to `interrupted`, and
   the caller classifies that as gate-execution infrastructure (never `gate-red`), preserving
   the audited rule that a host-terminated gate must not fabricate a product failure signature.
6. Evidence binding is untouched: `gate-report.json`, `evidenceBindingSha256`, exact-HEAD
   enforcement in `evidence-manifest.sh`, and the `dag.sh` validator behave byte-identically
   for a normally-completed gate.

## Acceptance Criteria

- New `tests/test-gate-attach.sh` (RED first): two concurrent identical gate launches today
  both execute (observation file written twice / both PIDs run); after the change the consumer
  command executes exactly once and both callers exit with the same result.
- Changed argv, env-allowlist value, or headSha prevents attachment (fresh job, both run).
- Killing the launcher leaves the gate running to completion under the supervisor; killing the
  supervisor reconciles `interrupted` and the driver classifies it as gate infrastructure.
- Prior gate artifacts survive until the fresh-path decision (no deletion on attach).
- Timeout semantics parity: a gate exceeding its budget still yields exit 124 and the existing
  `inconclusive-infrastructure` gate-report outcome.
- All three existing gate suites in the gate command pass unchanged.
